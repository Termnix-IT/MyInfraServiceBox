# MyInfraServiceBox 要件定義

## 目的

自宅のUbuntuサーバで、内部ネットワーク向けのWebサービス（DBを使うもの、バックエンド処理を持つものを含む）を動かすための基盤一式を、このrepoで管理する。各サービスのコードはそれぞれのrepoにあり、このrepoはそれらを載せる側として、入口となるまとめページ（ポータル）、共有DB、デプロイの仕組み、サーバの初期設定を持つ。

環境は1系統だけとし、デプロイした版がそのまま内部向けの本番になり、検証も同じ環境で行う。検証中の不具合で本番が壊れたままにならないよう、ブランチやcommitを指定したデプロイと、直前の版への切り戻しを用意する。

## 前提となるサーバ環境

- OSはUbuntu 24.04 LTSで、メモリは8GB。作業開始時点ではDockerは入っておらず、OSの標準構成に近い状態である。
- Minecraftサーバが基盤の外（Dockerを使わず）で不定期に動いており、TCP 25565番を使い、起動中は最大4GBのメモリを使う。基盤はこのサーバの設定に触れず、ポートとメモリを奪わないようにする。
- 利用者は宅内LANの端末だけで、外部（インターネット）には公開しない。
- このrepoはサーバ上の`/opt/myinfraservicebox`にcloneして使う。

## 主な決定事項

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| URL | ポート番号方式（ポータルは80番、各サービスは8100番台） | 宅内DNSの設定が不要で、サービスをサブパス配下で動かすための作り込みも要らないため |
| 実行方式 | Docker Compose | 依存関係がサーバ本体を汚さず、検証後の削除や再構築がしやすいため |
| 環境 | 1系統（staging／prodの分離なし） | メモリ8GBのうち半分をMinecraftが使うため、2系統分の余裕がないため。代わりに切り戻しで救済する |
| デプロイ契機 | サーバにSSHで入り、スクリプトを手動実行 | 外部から宅内サーバへ到達する経路を作らずに済むため。公開repoでself-hosted runnerを使う危険も避けられる |
| DB | 共有PostgreSQLを1台動かし、サービスごとにDBとユーザーを分ける | メモリ使用量を抑え、バックアップを1か所で管理できるため |
| アクセス制御 | 認証なし。UFWで宅内LAN以外からの通信を遮断する | 利用者がLAN内の自分だけで、ポータルは閲覧専用にするため |
| ポータル | 自作。Python + FastAPI + Jinja2 | デプロイ履歴との連携を自由に設計でき、フロントエンドのビルド工程を持たずに済むため |

## 構成要素

### サーバ初期設定

サーバの初期設定をスクリプトにまとめ、OSを入れ直した場合でも同じ状態を再現できるようにする。対象はDocker EngineとCompose pluginの導入、基盤用の共通Dockerネットワークの作成、UFWの設定（宅内LANから80・8100〜8199番への接続を許可するルールを追加し、SSHやMinecraftなど既存のルールは変更しない）、バックアップ用systemd timerの登録とする。スクリプトは何度実行しても同じ結果になるように作り、Minecraftの設定やファイルには触れない。

宅内LANのアドレス帯などの環境固有の値はrepoに含めず、サーバ上のgit管理外の設定ファイル（`.env`）から読み込む。

### 共有PostgreSQL

PostgreSQLを1台、このrepoのcompose構成で動かす。ポートはLANに公開せず、共通Dockerネットワーク内のサービスからだけ接続できるようにする。サービスごとにDBとユーザーを作るスクリプトを用意し、作ったパスワードはサーバ上のgit管理外の場所に保存する。

バックアップは、毎日systemd timerで全DBを`pg_dump`し、7世代を同じサーバに残して古いものを削除する。dumpからDBを復元する手順もスクリプトと手順書で用意する。保存先は設定で変えられるようにし、後からNASなど別の置き場所へのコピーを追加できる形にしておく。

### サービス台帳

基盤に載せるサービスを1つのファイル（`services.toml`）に登録し、ポータルとデプロイスクリプトの両方がこれを読む。登録する項目は次のとおり。

- 名前、説明、カテゴリ
- repoのURL（すべてpublic repoなので、認証なしでcloneする）
- 公開するポート番号
- ヘルスチェックの方式とパス（HTTPの`/health`、またはTCP接続）
- 共有PostgreSQLを使うかどうか
- 基盤の外で動くサービスかどうか（Minecraftはこれに当たり、TCP 25565番の死活確認だけを行う）

台帳には予約ポート（80番と25565番）も記載し、サービスへの割り当てに使えないようにする。

### デプロイスクリプト

サーバ上で次の形で実行する（コマンド名は仮）。

- `deploy <service> [--ref <branch|commit>]`：指定がなければ`main`の最新をデプロイする。
- `rollback <service>`：デプロイ履歴にある直前の成功した版へ戻す。

`deploy`は次の順で処理する。

1. 台帳を読み、ポートの重複や予約ポートの使用がないかを検査する。問題があれば何も変更せずに終了する。
2. 同じサービスへのデプロイが同時に走らないようにロックを取る。
3. サービスrepoをサーバ上の作業領域にcloneまたはfetchし、指定された版をcheckoutする。
4. サービスrepoの`compose.yaml`で`build`と`up`を行う。
5. ヘルスチェックが一定時間内に成功するかを確認する。失敗した場合は、直前の成功した版へ自動で戻す。
6. 結果（サービス名、指定したref、commit、日時、成否、切り戻しの有無）をデプロイ履歴に記録する。

デプロイ履歴はサーバ上のJSON Lines形式のファイルに追記し、ポータルはこれを読む。共有PostgreSQLに保存しないのは、DBが止まったときに履歴まで見えなくなり、原因の調査がしにくくなるためである。

### ポータル

FastAPIとJinja2で作るWebアプリで、80番で動かす。表示する内容は次のとおり。

- サービスの一覧と、各サービスへのリンク（台帳から作る）
- 各サービスの死活状態と応答時間（HTTPの`/health`、またはTCP接続で確認）
- 各サービスが動いているcommit、ref、デプロイ日時、直近のデプロイ結果（デプロイ履歴から作る）
- サーバのCPU・メモリ・ディスクの使用量と、各コンテナの状態

死活状態とリソースの表示は、ページを開いている間、少量のJavaScriptで定期的に更新する。ポータルは閲覧専用とし、デプロイ、再起動、停止などの操作機能は持たせない。将来操作機能を追加する場合は、その機能にだけ認証を追加する。

## サービスrepoとの取り決め

基盤に載せるサービスのrepoは、次のルールを守る。このルールを満たす見本として、最小のサンプルサービスの雛形を用意する。

- repoのルートに`Dockerfile`と`compose.yaml`を置く。
- 基盤の共通Dockerネットワークに参加する。
- LANに公開するポート番号は、台帳の値を環境変数で受け取る。
- HTTPで`/health`を提供し、正常なときに200を返す。
- 共有PostgreSQLを使う場合、接続先は環境変数`DATABASE_URL`で受け取る。
- コンテナにメモリ上限を指定する（目安は後述の「メモリ配分」に従う）。
- パスワードなどの秘密情報をrepoに含めない。

## メモリ配分

Minecraftの起動中を基準にメモリを配分する。8GBのうち、Minecraftに最大4GB、OSなどに約1GBが必要なので、基盤側のコンテナ全体で使えるのは約3GBとする。内訳の目安は、共有PostgreSQLに512MB、ポータルに256MB、残りの約2GBを各サービスに配分する。各サービスのメモリ上限は256MBを標準とし、それを超える場合は台帳に理由を書いたうえで個別に設定する。Minecraftが止まっている間は余裕が増えるが、上限は起動中を前提に決める。

## セキュリティ

このrepoは公開repoとして扱う。宅内LANのIPアドレス、パスワード、`.env`の内容はrepoに含めず、サーバ上のgit管理外のファイルに置く。repoには値を伏せた例示用のファイルだけを含める。

## 対象外とするもの

次の項目は、今回の要件に含めない。必要になった時点で要件を見直す。

- staging環境の用意（1系統で運用するため）
- サブドメインやパスによるルーティングと、リバースプロキシ
- HTTPS化
- 外部（インターネット）への公開とVPN経由のアクセス
- GitHub Actionsなどによる自動デプロイ
- ポータルからのデプロイや再起動などの操作

## 実装方針

要件を固めた後に選択肢を比較して決めた実装方針と、その理由を記す（2026-10時点の調査に基づく）。

### ポータルの実行方式

ポータルもDocker Composeで動かし、Dockerの状態はソケットプロキシ（`wollomatic/socket-proxy`）を経由して読む。Dockerソケットを直接マウントすると、`:ro`を付けてもDocker APIへの書き込みは防げず、ポータルが乗っ取られた場合にホストのroot権限まで奪われるためである。ソケットプロキシは正規表現でパスを許可できるものを選び、許可するのは`containers/json`（一覧と状態）と`containers/{id}/stats`（メモリ使用量）のGETだけにする。containers系のGETをまとめて許可するプロキシでは、環境変数に入ったDBのパスワードが見える`containers/{id}/json`や、コンテナ内のファイルを読める`archive`まで許可されてしまう。

ホスト全体のCPUとメモリは、コンテナ内から見える`/proc`（通常はホスト全体の値を示す）をpsutilで読む。値がずれる場合に限り、ホストの`/proc`を読み取り専用でマウントし`psutil.PROCFS_PATH`をそこへ向ける。ディスク使用量は、読み取り専用でマウントした`/var/lib/myinfraservicebox`のファイルシステムで測る。

### Dockerの公開ポートとUFW

Dockerが公開したポートへの通信はUFWのチェックより前に振り分けられるため、`DOCKER-USER`チェーンに「LAN側インターフェースから来た通信は、宅内LANのアドレス帯以外を捨てる」ルールを置き、`/etc/ufw/after.rules`に書いて永続化する。nftablesバックエンドはまだexperimentalで、将来既定になると`DOCKER-USER`の移行が必要になるため、`daemon.json`で`"firewall-backend": "iptables"`を明示して固定する。

ポータルのコンテナからホストの公開ポートへの死活確認はUFWのINPUTチェーンを通る場合があるため、共通Dockerネットワーク`infra`のアドレス帯から8100〜8199番と25565番への接続をUFWで許可する。既存のUFWルール（SSHやリモートデスクトップ用など）は変更せず、ルールの追加だけを行う。

### デプロイスクリプトと配置先

サーバ初期設定はaptやufwの操作が中心なのでBashで書き、それ以外の操作（デプロイ、切り戻し、DB作成、バックアップ、復元）はPythonの`infra`コマンドにまとめる。`infra`コマンドは標準ライブラリだけで動かし、サーバにはOS標準のPython 3.12以外を入れない。台帳をYAMLではなくTOMLにしたのは、標準の`tomllib`で読めるためである。台帳の読み込みと検査のコードはポータルと共有し、デプロイとポータルで台帳の解釈がずれないようにする。

| 用途 | 配置先 |
| --- | --- |
| このrepo | `/opt/myinfraservicebox` |
| 環境固有の設定（LANのアドレス帯など） | `/etc/myinfraservicebox/infra.env` |
| 秘密情報（DBのパスワードなど） | `/etc/myinfraservicebox/secrets/` |
| サービスrepoのclone、デプロイ履歴、ロック | `/var/lib/myinfraservicebox/` |
| PostgreSQLのバックアップ | `/var/backups/myinfraservicebox/postgres/` |

切り戻しでは前の版のイメージをビルドし直す。ビルドキャッシュが効くため多くは短時間で終わるが、サービスによっては数分かかることを許容する。
